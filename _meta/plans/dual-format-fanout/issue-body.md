## Problem

The ruled fan-out shape is: `plugin/core` (harness-pure domain library) and `plugin/mcp` (the
shared stdio MCP server) are authored once, and a production step emits each harness's instance
from that one source — never a second, hand-maintained implementation. That authored core already
exists and is harness-pure (`plugin/README.md:5-11`; enforced by
`node scripts/check-core-purity.mjs`, CLAUDE.md:114).

The Claude Code side of that "production step" pattern already ships and works — this is new since
the issue was last edited, and resolves what its body previously listed as a deferred packaging
gap:

- `plugins/desk-standard/` (not `plugin/claude-plugin/`) is the live marketplace bundle; it moved
  there in PR #191 (`59556b9`, "extract marketplace bundles to top-level plugins/ tree"). The old
  `plugin/claude-plugin/` path is now an empty, vestigial directory (`plugin/claude-plugin/`
  contains only a stray `.DS_Store`, confirmed on disk).
- The previously-recorded deferred item — "a marketplace-installed Claude plugin needs `mcp/` +
  `core/` bundled inside the plugin dir; the shipped `.mcp.json` used a repo-local
  `${CLAUDE_PLUGIN_ROOT}/../mcp/server.ts` wiring" — is **resolved**. The shipped
  `plugins/desk-standard/.mcp.json` now points at a **self-contained, committed** bundle:
  `{"command": "bun", "args": ["${CLAUDE_PLUGIN_ROOT}/mcp/server.js"]}`
  (`plugins/desk-standard/.mcp.json:2-4`). That `server.js` (757KB, includes its own deps) plus the
  schema copies are regenerated by `cd plugin && bun run package` (`plugin/package.json:17`), and a
  CI drift guard (`.github/workflows/ci.yml:139-147`, `git diff --exit-code` against
  `plugins/desk-standard/`) fails the build if the committed artifact drifts from source. This IS
  the production-step pattern the OpenCode instance would need to mirror — no build-time gap
  remains on the Claude side.
- `docs/build-brief.md`, the doc the previous body cited for its acceptance criteria (AC1/AC3) and
  deliverables (D4/D5), no longer exists at that path (confirmed missing), nor does
  `_meta/build-brief.md` (also confirmed missing — referenced only historically, e.g.
  `docs/development/README.md:62`, `schema/README.md:9,54`). The project's canonical direction page
  is now `docs/CHARTER.md` (CLAUDE.md:1-3, "if that page and this one ever disagree about
  direction, the charter wins"); it states plainly: **"Scope is Claude Code only in v1; OpenCode is
  a deferred, separate fan-out build"** (`docs/CHARTER.md:38`).

No production step exists yet for an OpenCode instance. `plugin/opencode/` holds a **frozen,
unwired hand-written adapter spike** (`plugin/opencode/plugin.ts`, 98 lines: `resolvePluginRoot`,
`mcpServerCommand`, `registerMcpServer`, a `DeskStandard: Plugin` export registering the same
shared MCP server via OpenCode's `config` hook) — a preserved partial build from before the "common
core -> production step" shape was ruled, explicitly kept only as design reference, not a surface
to extend: "treat it as an artifact of record, not a surface to extend"
(`plugin/opencode/README.md:1,7-16`). It is excluded from the build and the shipped manifest
(the `tsc` include covers only core+mcp; the marketplace copies only `plugins/desk-standard/`),
though its unit tests still run under the default suite -- `plugin/package.json:13` scopes
`"test"` to `bun test core mcp opencode desk-persona`, which `make test` and CI both invoke
(`.github/workflows/ci.yml:151`). The spike's own README's "wired into nothing" wording
(`plugin/opencode/README.md:12-14`) is stale on that one point.

ADR 0021 (the graduated 1.0.0 direction record) confirms the park is unaffected by anything ruled
for 1.0.0: "What 0021 does NOT change (recorded for completeness): the Claude-only v1 scope (Claude
+ OpenCode dual-format stays post-1.0)" (`docs/decisions/0021-desk-standard-1-0-0-direction.md:102-104`).

## Deliverables

- **A — one production step, both instances.** Extend (or add a sibling to) the existing
  `bun run package` build step (`plugin/package.json:17`) so it emits the Claude instance (as
  today, at `plugins/desk-standard/`) and a new OpenCode instance from the same `plugin/core` +
  `plugin/mcp` source — neither instance hand-maintains a duplicate of MCP server code, schema, or
  skills content; both stay mechanically regenerable.
- **B — OpenCode instance registers the shared MCP server.** The generated instance registers the
  same four tools (`profile_get`, `profile_validate`, `template_render`, `knowledge_index`) via
  OpenCode's `config` hook, with no tool re-implemented as an OpenCode-native tool and no double
  registration — the idempotency contract the frozen spike already demonstrates
  (`registerMcpServer`, `plugin/opencode/plugin.ts:68-77`, "never double-registers").
- **C — fidelity-loss documentation.** Any capability that cannot port 1:1 between the two harness
  formats ("port the capability, not the implementation") is documented explicitly, not silently
  dropped — including the null case ("no fidelity loss found") if that's what the build finds.
- **D — drift + neutrality coverage extended.** The new OpenCode-instance-emitting artifacts get
  the same class of drift guard the Claude bundle already has (regenerate -> `git diff
  --exit-code`, pattern at `.github/workflows/ci.yml:139-147`), and stay inside
  `check-neutrality.mjs`'s existing scan scope (`plugin/` + `librarian/` recursively).

## Acceptance criteria

- [ ] `plugins/desk-standard/` (Claude instance) and a new OpenCode instance are both produced by
      ONE build/production step reading from `plugin/core` + `plugin/mcp` — zero hand-maintained
      duplicate of MCP server code, schema, or skills content in either instance.
- [ ] The OpenCode instance registers the same shared MCP server (four tools) via OpenCode's
      `config` hook; `bun test` (or an equivalent OpenCode-side test) proves zero double
      registration and zero tool re-implementation.
- [ ] Both instances load cleanly in their own harness (a Claude Code session with the plugin
      enabled; an OpenCode session with the plugin loaded) with no manual post-generation edit.
- [ ] A fidelity-loss note (or an explicit "none found") ships with the build for any capability
      that cannot port 1:1 across formats.
- [ ] Regenerating the OpenCode instance and running `git diff --exit-code` against its committed
      output is clean in CI (mirrors `.github/workflows/ci.yml:139-147`'s existing Claude-side
      check) — a hand-edited generated artifact is caught, not silently accepted.
- [ ] `node scripts/check-neutrality.mjs` passes with the new OpenCode instance included in its
      scan (scope: `plugin/` + `librarian/` recursively).
